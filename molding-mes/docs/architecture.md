# 架构说明

## 1. 分层

```
┌──────────────────────────────────────────────────────┐
│ 客户端层                                              │
│   安卓 APP（Kotlin + Compose，读写：下单/报工/出库）    │
│   微信小程序（原生，只读看板：按手机号判定可见范围）     │
│   管理后台（原生 HTML/JS，静态托管 /admin/）            │
└───────────────┬──────────────────────┬───────────────┘
                │ HTTPS / JSON          │ 静态托管 /admin/
┌───────────────▼──────────────────────▼───────────────┐
│ 接口层  Fastify                                       │
│   middleware：JWT → 用户装载 → 租户授权校验 → 角色鉴权  │
│   modules：auth / platform / admin / master /         │
│             orders / schedule / notify / chat / mp    │
└───────────────┬──────────────────────────────────────┘
┌───────────────▼──────────────────────────────────────┐
│ 领域层                                                │
│   scheduler.js  排产引擎（CP-SAT + 列表调度降级）       │
│   material.js   物料与标签核算、齐套判定                │
│   mpview.js     小程序视图聚合（按可见范围裁剪数据）     │
│   nlp.js        AI 解析 + 确定性兜底                   │
│   notify.js     按角色 + 机台的消息生成                 │
│   wechat.js     jscode2session / 手机号快速验证         │
└───────────────┬──────────────────────────────────────┘
┌───────────────▼──────────────────────────────────────┐
│ 数据层  SQLite(node:sqlite) / MySQL(mysql2)           │
│   schema.js 单一事实源 → 生成两种方言 DDL              │
└──────────────────────────────────────────────────────┘
```

## 2. 多租户模型

```
Tenant（公司）                      注册：平台运维用平台口令创建
 ├── license：max_users / expires_at / status
 ├── ai_configs：BaseURL / APIKey / 模型（公司独立配置）
 ├── users：phone（唯一）/ role / machine_code（可空）
 └── 全部业务表都带 tenant_id，查询一律带租户条件
```

**授权写入口是唯一的**：员工必须被管理员录入手机号才能登录。
登录时若手机号不存在，直接返回 `NOT_AUTHORIZED` 并提示联系本公司管理员——
这保证「拿到 APP 安装包」不等于「能进系统」。

## 3. 一次下单的完整时序

```
业务员 APP
  │ POST /api/chat {text}
  ▼
chat.js
  ├─ 载入本公司主数据（产品/别名/客户/模具/原料/标签）
  ├─ parseUtterance()
  │    ├─ 有 APIKey → OpenAI 兼容协议，系统提示词注入主数据
  │    └─ 无 Key / 失败 → fallbackParse（关键词+中文数量日期+词典相似度）
  ├─ 实体落地：产品与客户必须在台账中匹配到，否则返回候选待确认
  ├─ 建订单（status=DRAFT）
  └─ runAndPersistSchedule()
       ├─ runScheduling()         排产引擎
       ├─ 清旧计划 → 写 schedule_tasks / material_plans
       └─ pushScheduleNotifications()
            ├─ MATERIAL_PLAN   → 配料员
            ├─ ORDER_CREATED   → 生产人员（按机台定向）
            ├─ MOLD_CHANGE     → 技术员
            ├─ *_SHORTAGE      → 仓库
            └─ DELAY_RISK      → 业务员
```

## 4. 为什么 AI 解析必须有兜底

车间网络不稳定、Key 会过期、供应商会限流。如果解析是唯一路径，AI 一挂，
整条生产线的信息流就断了。因此系统设计为**双通道**：

| 通道 | 触发 | 能力 | 依赖 |
|---|---|---|---|
| AI 解析 | 已配置 APIKey 且调用成功 | 理解口语化、省略、倒装表达 | 外网 / 私有化模型 |
| 确定性兜底 | 未配置 Key、超时、报错、返回非法 JSON | 关键词判意图 + 中文数量/日期 + 词典相似度 | 无 |

两条通道**输出同一套结构**（intent / payload / confidence / candidates），
上层业务代码不做分支，因此可以无缝切换。

## 5. 数据严谨性设计

延续专家团的治理口径：

1. **不静默填充**：AI 没匹配上的产品不猜，返回候选让用户确认
2. **效率不编造**：机台×模具没有实测效率且无默认值时，该机台直接不参与排产
3. **硬约束可阻断**：供料线故障连带封锁机台，写进排产引擎而非事后提醒
4. **建档完成度可见**：`/api/master/onboarding` 告诉管理员缺什么、缺了影响什么
5. **审计留痕**：主数据改动、下单、出库、排产全部写 `audit_logs`
6. **解析留痕**：每句自然语言写 `ai_parse_logs`，便于回溯与提示词调优

## 6. 微信小程序端要点（v3.2）

- **只读**：报工、出库、下单仍在安卓 APP，小程序不写业务数据，避免双写冲突
- **权限四道关**：微信 openid → 是本公司在职员工 → 在小程序白名单且启用 → 视图可见性
- **白名单只认手机号**：`wx_access(tenant_id, phone)` 由公司管理员维护；取消授权会同时置空已绑定微信身份
- **视图可逐人覆盖**：`wx_access.views` 非空则以勾选为准，否则走角色默认（`ROLE_VIEWS`）
- **登录态每次复核**：即便 openid 已绑定，登录时仍重新校验白名单与账号状态，管理员随时可关
- **微信能力**：`lib/wechat.js` 封装 `jscode2session`、`stable_token`、`getuserphonenumber`；
  未配置凭证且非生产环境时可开 `WX_DEV_MODE` 用手机号直登，便于联调
- **保养期不臆测**：只给剩余模次与已用百分比；仅当存在最近排产效率时才推算到期天数并标注依据
- **换模时间可溯**：由开工时间反推（换模工时 + 30 分钟缓冲），页面写明推导口径

## 7. 安卓端要点

- **会话**：SharedPreferences 存 token；服务端地址可在「我的」页改（适配内网部署）
- **角色自适应首页**：生产人员看当班计划、配料员看配料计划、技术员看模具提醒
- **机台绑定**：生产人员可绑定机台（只收本机台消息），也可不绑定（收全部）——
  这一条是通用性要求，同一套代码适配「专人专机」与「全线通岗」两种班组形态
- **消息**：WorkManager 15 分钟轮询 + 本地通知；接入 FCM 时只需替换 `PollWorker`
